# 泛型程序设计

在前面我们学习了最重要的类和对象，了解了面向对象编程的思想，注意，非常重要，面向对象是必须要深入理解和掌握的内容，不能草草结束。在本章节，我们还会继续深入了解，从泛型开始，再到数据结构，最后再开始我们的集合类学习，循序渐进。


### 泛型类
泛型在Java非常重要，我们可以使用一个特殊的名字表示待定类型，在泛型类中，我们可以将这个待定类型添加到类名后，它通常也被称为**类型参数**（Type Parameter）泛型在定义时并不明确是什么类型，而是需要到使用时才会确定具体的类型。

我们可以将一个类定义为一个泛型类：
```java
public class Score<T> {   //泛型类需要使用<>，我们需要在里面添加1 - N个类型参数
    String name;
    String id;
    T value;   //T会根据使用时提供的类型自动变成对应类型

    public Score(String name, String id, T value) {   //这里T可以是任何类型，但是一旦确定，那么就不能修改了。
        this.name = name;
        this.id = id;
        this.value = value;
    }
}
```

我们来看看这是如何使用的：
```java
public static void main(String[] args) {
    Score<String> score = new Score<String>("计算机网络", "EP074512", "优秀");
  	//因为现在有了类型变量，在使用时同样需要跟上<>并在其中填写明确要使用的类型
  	//这样我们就可以根据不同的类型进行选择了
    String value = score.value;   //一旦类型明确，那么泛型就变成对应的类型了
    System.out.println(value);
}
```
### ==注意，基本类型不能参与泛型==

泛型将数据类型的确定控制在了编译阶段，在编写代码的时候就能明确泛型的类型，如果类型不符合，将无法通过编译！因为是具体使用对象时才会明确具体类型，所以说静态方法中是不能用的：
```java
Score<String> score1 = new Score<>("语文", "001", "优秀");     // 这个对象里 T = String
Score<Integer> score2 = new Score<>("数学", "002", 95);         // 这个对象里 T = Integer
```
注意：**`score1` 和 `score2` 都是 `Score` 类的对象，但它们各自的 T 是不同的**。这一点非常关键——泛型的类型参数，是**绑定在"实例"上的**，不是绑定在"类"上的。
现在问题来了：静态方法/静态字段，属于**类本身**，不属于任何一个具体对象。
```java
public class Score<T> {
    T value;              // 实例字段：属于每一个对象，可以用 T
    
    static T defaultValue; // ❌ 编译报错！
    
    static void show(T value) { // ❌ 编译报错！
        System.out.println(value);
    }
}
```
就算已经创建了对象，`score1` 的 T 是 String，`score2` 的 T 是 Integer，而 `defaultValue` 是**全类共享的唯一一份**——它到底该是 String 还是 Integer？没法回答，因为它俩都成立又都不成立。

所以本质原因是：**静态成员的生命周期比"类型参数被确定"这件事更早、更宽泛**。静态成员在类加载时就有了，且是所有实例共享的唯一一份；而 T 是每个实例各自私有的、要等到 `new` 的时候才明确。二者的"生命周期"和"归属范围"根本对不上，编译器自然不允许你在静态上下文里用类的类型参数。


那静态方法就完全不能用泛型了吗？—— 不是！
```java
public class Score<T> {
    T value;

    // 这里的 <E> 是这个方法自己声明的类型参数，不是类的 T
    // 每次调用这个静态方法时，E 会根据传入参数临时确定
    public static <E> void print(E content) {
        System.out.println(content);
    }
}
```
调用时：
```java
Score.print("hello");   // 这次调用，E = String
Score.print(123);       // 这次调用，E = Integer
```
区别在哪？**方法级别的泛型 `<E>`，是在"方法被调用"这一刻确定的，而不是靠对象**。每次调用都可以传不同类型，互不冲突，因为它不依赖任何"共享唯一份"的东西，天然就没有前面说的矛盾。


我们在方法中使用待确定类型的变量时，因为此时并不明确具体是什么类型，那么默认会认为这个变量是一个Object类型的变量，因为无论具体类型是什么，一定是Object类的子类：
![[Pasted image 20260726171710.png]]


不能通过这个不确定的类型变量就去直接创建对象和对应的数组：
```java
class Test<T> {   // T 是类型形参（泛型参数）
    void test() {
        new T();    // ❌ 编译错误：类型形参 'T' 不能直接实例化
    }
}
```


具体类型不同的泛型类变量，不能使用不同的变量进行接收：
![[Pasted image 20260726171832.png]]

那如果T没用到会不会报错？
```java
public class Score<T> {   // T 声明了，但类里压根没用到
    private String name;
    private String id;
    private String value;
    // 没有任何字段是 T 类型，构造方法、方法参数也都没用到 T
}
```
```java
Score<String> score1 = new Score<>();
Score<Integer> score2 = score1;   // ❌ 依然编译报错
```
**结论不变，还是报错**。原因是：Java 编译器在做泛型类型检查的时候，**只看你类型声明时尖括号里写的类型参数**（`Score<String>` vs `Score<Integer>`），完全不会去分析这个类内部到底有没有真正用到 `T`。也就是说，编译器判断"这两个类型兼不兼容"，走的是一套纯粹基于**声明**的规则，而不是基于"实际用没用到"的规则。哪怕 `T` 在 `Score` 类里一次都没出现过，`Score<String>` 和 `Score<Integer>` 在编译器眼里依然是两个不同、不兼容的类型。

如果要让某个变量支持引用确定了任意类型的泛型，那么可以使用`?`通配符：
```java
Score<?> score2 = score1;   // ✅ 合法！<?> 表示"不确定具体是什么类型，但接受任意一种"
}
```

如果使用通配符，那么由于类型不确定，所以说具体类型同样会变成Object:
```java
Score<?> score = new Score<>();//一般来说会直接把类型写出来，除非像接受所有类型
Object value = score.value;
```

### 泛型与多态

不只是类，包括接口、抽象类，都是可以支持泛型的：
```java
public interface Study<T> {
    T test();
}
```
当子类实现此接口时，我们可以选择在实现类明确泛型类型，或是继续使用此泛型让具体创建的对象来确定类型：
```java
public class Main {
    public static void main(String[] args) {
        A a = new A();
        Integer i = a.test();
    }

    static class A implements Study<Integer> {   
      	//在实现接口或是继承父类时，如果子类是一个普通类，那么可以直接明确对应类型
        @Override
        public Integer test() {
            return null;
        }
    }
}
```

用来承接泛型的接口的类也可以使用泛型：
```java
public class Main {
    public static void main(String[] args) {
        A<String> a = new A<>();
        String i = a.test();
    }

    static class A<T> implements Study<T> {   
      	//让子类继续为一个泛型类，那么可以不用明确
        @Override
        public T test() {
            return null;
        }
    }
}
```

继承也是同样的：
```java
static class A<T> {
    
}

static class B extends A<String> {

}
```


### 泛型方法
泛型方法指的是：**方法自己声明了独立的类型参数**，这个类型参数只在这个方法内部有效，跟这个方法所在的类是不是泛型类没有关系。
```java
public class Test {
    // <T> 写在返回值类型前面，声明这是一个泛型方法
    public static <T> void show(T value) {
        System.out.println(value);
    }
}
```

```java
Test.show("Hello");   // T 被推断为 String
Test.show(100);       // T 被推断为 Integer
Test.show(3.14);      // T 被推断为 Double
```
关键的语法点：`<T>` 写在**修饰符之后、返回值类型之前**。这个位置很重要，也是泛型方法最典型的标志——只要方法签名里返回值前面出现了 `<T>`，就说明这是一个泛型方法。


泛型方法 vs 泛型类，核心区别是什么
```java
// 泛型类：T 属于整个类，new 对象时就要确定
public class Box<T> {
    private T value;
    public T get() { return value; }
    public void set(T value) { this.value = value; }
}
```

```java
// 泛型方法：T 只属于这一个方法，跟类无关
public class Utils {
    public static <T> T getFirst(T[] arr) {
        return arr[0];
    }
}
```
区别一句话概括：**泛型类的 `T` 在创建对象（`new Box<String>()`）时就确定了，之后类里所有用到 `T` 的地方都是同一个类型；泛型方法的 `T` 是每次调用方法时才确定，只在这一次方法调用里有效，跟类完全无关，甚至这个方法所在的类根本不需要是泛型类**。
```java
Utils.getFirst(new String[]{"a", "b"});   // 这次调用，T 是 String
Utils.getFirst(new Integer[]{1, 2, 3});   // 这次调用，T 是 Integer
// Utils 类本身自始至终都不是泛型类，跟 T 一点关系都没有
```



### 泛型的界限
现在有一个新的需求，现在没有String类型的成绩了，但是成绩依然可能是整数，也可能是小数，这时我们不希望用户将泛型指定为除数字类型外的其他类型，我们就需要使用到泛型的上界定义：
```java
public class Score<T extends Number> {   //设定类型参数上界，必须是Number或是Number的子类
    private final String name;
    private final String id;
    private final T value;

    public Score(String name, String id, T value) {
        this.name = name;
        this.id = id;
        this.value = value;
    }

    public T getValue() {
        return value;
    }
}
```
只需要在泛型变量的后面添加`extends`关键字即可指定上界，使用时，具体类型只能是我们指定的上界类型或是上界类型的子类，不得是其他类型。否则一律报错：
![[Pasted image 20260727164037.png]]
实际上就像这样：
![[Pasted image 20260727164241.png]]



同样的，当我们在使用变量时，泛型通配符也支持泛型的界限：
```java
public static void main(String[] args) {
    Score<? extends Integer> score = new Score<>("数据结构与算法", "EP074512", 60);
}
```
`? extends Number` 的意思是："这个 `Score` 内部装的具体类型是**不确定的，但可以确定它一定是 `Number` 或者 `Number` 的某个子类**"——可能是 `Integer`、`Double`、`Long`，但**绝不可能**是 `Number` 的父类（因为 `Number` 已经是 `Object` 的直接子类了，不会有比 `Number` 更"低"、又满足 `extends Number` 的类型）。

既然编译器能确定"不管具体是哪个类型，反正肯定是 `Number` 家族的成员"，那读取出来的东西，**至少可以放心当 `Number` 用**——因为不管里面是 `Integer` 还是 `Double`，它们全都是 `Number` 的子类，都能安全地向上转型成 `Number`


那么既然泛型有上界，那么有没有下界呢？肯定的啊：
![[Pasted image 20260727164329.png]]
只不过下界仅适用于通配符，对于类型变量来说是不支持的。下界限定就像这样：

那么限定了上界后，我们再来使用这个对象的泛型成员，会变成什么类型呢？
```java
public static void main(String[] args) {
    Score<? extends Number> score = new Score<>("数据结构与算法基础", "EP074512", 10);
    Number o = score.getValue();   //可以看到，此时虽然使用的是通配符，但是不再是Object类型，而是对应的上界
}
```

但是我们限定下界的话，因为还是有可能是Object，所以说依然是跟之前一样：
```java
public static void main(String[] args) {
    Score<? super Number> score = new Score<>("数据结构与算法基础", "EP074512", 10);
    Object o = score.getValue();
}
```
`? super Number` 的意思是："这个 `Score` 内部装的具体类型是**不确定的，但可以确定它一定是 `Number` 或者 `Number` 的某个父类**"——可能是 `Number` 本身，也可能是 `Object`（因为 `Object` 是所有类的父类，自然也是 `Number` 的父类）。
问题就出在这里：**父类可以有很多层，Java 没法确定具体是哪一层**。举个例子，假设有这样的继承关系：
```
Object → Number → Integer
```

`? super Number` 可能对应的实际类型是 `Number` 本身，也可能是更高层的 `Object`。既然连"到底是 `Number` 还是 `Object`"都无法确定，编译器只能选一个**在任何情况下都绝对安全**的类型来接收返回值——那就只剩下 `Object`，因为无论实际是 `Number` 还是 `Object`，用 `Object` 接收总是成立的：
```java
Object o = score.getValue();   // 只能用 Object 接收，没法更精确了
// Number n = score.getValue();  // ❌ 编译错误！万一实际类型是 Object，这样接收就不安全
```

### 类型擦除
前面我们已经了解如何使用泛型，那么泛型到底是如何实现的呢，程序编译之后的样子是什么样的？
```java
public abstract class A <T>{
    abstract T test(T t);
}
```

实际上在Java中并不是真的有泛型类型（为了兼容之前的Java版本）因为所有的对象都是属于一个普通的类型，一个泛型类型编译之后，实际上会直接使用默认的类型：
```java
public abstract class A {
    abstract Object test(Object t);  //默认就是Object
}
```
当然，如果我们给类型变量设定了上界，那么会从默认类型变成上界定义的类型：
```java
public abstract class A <T extends Number>{   //设定上界为Number
    abstract T test(T t);
}
```
那么编译之后：
```java
public abstract class A {
    abstract Number test(Number t);  //上界Number，因为现在只可能出现Number的子类
}
```

因此，泛型其实仅仅是在编译阶段进行类型检查，当程序在运行时，并不会真的去检查对应类型，所以说哪怕是我们不去指定类型也可以直接使用：
```java
public static void main(String[] args) {
    Test test = new Test();    //对于泛型类Test，不指定具体类型也是可以的，默认就是原始类型
}
```
只不过此时编译器会给出警告：
![[Pasted image 20260727170843.png]]

同样的，由于类型擦除，实际上我们在使用时，编译后的代码是进行了强制类型转换的：
```java
public static void main(String[] args) {
    A<String> a = new B();
    String  i = a.test("10");     //因为类型A只有返回值为原始类型Object的方法
}
```

实际上编译之后：
```java
public static void main(String[] args) {
    A a = new B();
    String i = (String) a.test("10");   //依靠强制类型转换完成的
}
```

不过，我们思考一个问题，既然继承泛型类之后可以明确具体类型，那么为什么`@Override`不会出现错误呢？我们前面说了，重写的条件是需要和父类的返回值类型和形参一致，而泛型默认的原始类型是Object类型，子类明确后变为其他类型，这显然不满足重写的条件，但是为什么依然能编译通过呢？

```java
public class B extends A<String>{
    @Override
    String test(String s) {
        return null;
    }
}
```

我们来看看编译之后长啥样：
```java
// Compiled from "B.java"
public class com.test.entity.B extends com.test.entity.A<java.lang.String> {
  public com.test.entity.B();
  java.lang.String test(java.lang.String);
  java.lang.Object test(java.lang.Object);   //桥接方法，这才是真正重写的方法，但是使用时会调用上面的方法
}
```

通过反编译进行观察，实际上是编译器帮助我们生成了一个桥接方法用于支持重写：
```java
public class B extends A {
    
    public Object test(Object obj) {   //这才是重写的桥接方法
        return this.test((Integer) obj);   //桥接方法调用我们自己写的方法
    }
    
    public String test(String str) {   //我们自己写的方法
        return null;
    }
}
```

类型擦除机制其实就是为了方便使用后面集合类（不然每次都要强制类型转换）同时为了向下兼容采取的方案。因此，泛型的使用会有一些限制：

首先，在进行类型判断时，不允许使用泛型，只能使用原始类型：
![[Pasted image 20260727172317.png]]
只能判断是不是原始类型，里面的具体类型是不支持的，泛型不能和instanceof一起用：
```java
Test<String> test = new Test<>();
System.out.println(test instanceof Test);   //在进行类型判断时，不允许使用泛型，只能使用原始类型
```

还有，泛型类型是不支持创建参数化类型数组的：
![[Pasted image 20260727172342.png]]

要用只能用原始类型：
```java
public static void main(String[] args) {
    Test[] test = new Test[10];   //同样是因为类型擦除导致的，运行时可不会去检查具体类型是什么
}
```


**Java 的泛型只存在于源代码和编译阶段，一旦编译成 `.class` 字节码，所有泛型的具体类型信息都会被"擦掉"，替换成普通的类型。** 这就是类型擦除（Type Erasure）。
换句话说：你写代码的时候用 `List<String>`、`Score<Integer>` 这些"看起来带类型"的写法，是为了让**编译器**在编译阶段帮你做类型检查；但编译完之后，运行时的 JVM **压根不知道、也不关心**曾经有过 `<String>`、`<Integer>` 这回事，一切都被还原成了没有泛型之前的样子。

**你写的代码（擦除前）：**
```java
public class Box<T> {
    private T value;
    
    public T getValue() {
        return value;
    }
    
    public void setValue(T value) {
        this.value = value;
    }
}
```

**编译成字节码后，大致相当于（擦除后）：**
```java
public class Box {
    private Object value;   // T 没有上界，擦除成 Object
    
    public Object getValue() {
        return value;
    }
    
    public void setValue(Object value) {
        this.value = value;
    }
}
```

`T` 这个字母、`<T>` 这个尖括号，编译完之后就**彻底不存在了**，`class Box.class` 这个文件里看不到任何关于 `T` 的痕迹，只剩下一个用 `Object` 存值的普通类。



#### 那既然最后都是Object，为什么还会报错？
![[Pasted image 20260727192613.png]]

#####  先明确：报错发生在编译阶段，而擦除发生在编译的"最后一步"
```java
Test<Integer> test = new Test<>(10);
Test<String> test1 = test;   // ❌ 这里报错
```

这行报错，是 Java 编译器在**编译期类型检查**阶段就直接拦下来的，报错信息也写得很清楚：

```
必需类型: Test<String>
已提供:   Test<Integer>
```

关键在于——**这个检查发生的时间点，是在类型擦除之前**。你可以把整个编译过程想象成两个先后独立的阶段：

```
第一阶段（编译期）：严格按照你写的 Test<Integer>、Test<String> 这些"完整"的泛型类型信息，检查类型是否兼容
                    ↓（检查通过后）
第二阶段（生成字节码时）：才把这些泛型类型信息全部擦除，Test<Integer>、Test<String> 都变成 Test
```

你的代码根本走不到第二阶段——因为第一阶段的类型检查就已经失败了，编译器直接报错，压根不会继续往下走到"擦除"这一步。

### 线性表：顺序表
```java
public class ArrayList<E> {
    private int capacity = 10;// 容器容量：这个数组总共能装多少个元素（这里是10个空位）
    private int size = 0;// 元素个数：目前数组里实际存了多少个"真实数据"
    private Object[] array = new Object[capacity];// 真正分配的数组空间，长度是10

    public void add(E element, int index) {
        // 校验index合法性，防止越界
        if (index < 0 || index > size) {
            throw new IndexOutOfBoundsException("Index: " + index + ", Size: " + size);
        }
        // 把 index 到 size-1 的元素，依次往后挪一位，注意从 size 开始，倒着挪
        for (int i = size; i > index; i--) {
            array[i] = array[i - 1];
        }
        // 挪完之后，index 这个位置空出来了，放新元素
        array[index] = element;
        // 只在最后加一次
        size++;
    }
}
```

只不过依然不够完美，万一我们的顺序表装满了咋办？所以说，我们在插入元素之前，需要进行判断，如果已经装满了，那么我们需要先扩容之后才能继续插入新的元素：
```java
public void add(E element, int index){
    if(index < 0 || index > size)
        throw new IndexOutOfBoundsException("插入位置非法，合法的插入位置为：0 ~ "+size);
    if(capacity == size) {
        int newCapacity = capacity + (capacity >> 1);   //扩容规则就按照原本容量的1.5倍来吧
        Object[] newArray = new Object[newCapacity];    //创建一个新的数组来存放更多的元素
        System.arraycopy(array, 0, newArray, 0, size);   //使用arraycopy快速拷贝原数组内容到新的数组
        array = newArray;   //更换为新的数组
      	capacity = newCapacity;   //容量变成扩容之后的
    }
    for (int i = size; i > index; i--)
        array[i] = array[i - 1];
    array[index] = element;
    size++;
}
```

试一下
```java
public static void main(String[] args) {
    ArrayList<Integer> list = new ArrayList<>();
    for (int i = 0; i < 20; i++)
        list.add(i, i);
    System.out.println(list);
}
```


我们接着来看删除操作，其实操作差不多，只需要将后面的覆盖到前面就可以了：
```java
@SuppressWarnings("unchecked")   //屏蔽未经检查警告
public E remove(int index){   //删除对应位置上的元素，注意需要返回被删除的元素
    E e = (E) array[index];   //因为存放的是Object类型，这里需要强制类型转换为E
    for (int i = index; i < size; i++)   //从前往后，挨个往前搬一位
        array[i] = array[i + 1];
    size--;    //删完记得将size--
    return e;
}
```


### 线性表：链表
这一段就是网页里"线性表：链表"这一节的完整内容，我把每一段代码都逐行拆开讲清楚。这份代码和你之前自己写的、以及我们聊过的 `Node<E>` 版本几乎是同一个思路，正好可以互相印证。

## 1. 链表的基本定义

```java
public class LinkedList<E> {
    // 链表的头结点，用于连接之后的所有结点
    private final Node<E> head = new Node<>(null);
    private int size = 0;   // 当前的元素数量还是要存一下，方便后面操作

    private static class Node<E> {  // 结点类，仅供内部使用
        E element;   // 每个结点都存放元素
        Node<E> next;   // 以及指向下一个结点的引用

        public Node(E element) {
            this.element = element;
        }
    }
}
```

逐行讲：

- `private final Node<E> head = new Node<>(null);` —— 这是**头节点**，之前详细讲过：它是一个真实存在的 `Node` 对象，`element` 是 `null`，专门当"起点标记"用（哨兵节点），加了 `final` 是因为头节点这个引用一旦创建就不应该再被改指向别的对象（链表结构变化靠的是修改各个节点的 `next`，而不是替换 `head` 本身）。
- `private int size = 0;` —— 记录当前链表里真实元素的个数。
- `private static class Node<E> { ... }` —— 节点类，`static` 说明它不依赖外部类实例（之前详细讲过原因）。
- `E element;` / `Node<E> next;` —— 节点存的数据、以及指向下一个节点的引用。
- 构造方法只接收 `element`，`next` 保持默认值 `null`。

## 2. 插入操作（未做校验的版本）

```java
public void add(E element, int index){
    Node<E> prev = head;   // 先找到对应位置的前驱结点
    for (int i = 0; i < index; i++)
        prev = prev.next;
    Node<E> node = new Node<>(element);   // 创建新的结点
    node.next = prev.next;   // 先让新的节点指向原本在这个位置上的结点
    prev.next = node;   // 然后让前驱结点指向当前结点
    size++;   // 完事之后一样的，更新size
}
```

逐行讲：

- `Node<E> prev = head;` —— `prev`（前驱，"前一个"的意思）从头节点出发，因为要在 `index` 位置插入，必须先找到 `index` 前面那个节点，才能把新节点接进去（回顾之前讲过的：想操作某个节点，得先拿到它前面那个节点）。
- `for (int i = 0; i < index; i++) prev = prev.next;` —— 循环 `index` 次，每次把 `prev` 往后移一位。举例：`index = 2` 时，循环执行2次，`prev` 从 `head` 移动到"第0个真实节点"，再移动到"第1个真实节点"——最终 `prev` 正好停在"第2个位置"的**前一个**节点上，也就是原来下标1的节点（因为 `head` 本身不算真实数据，`head.next` 才是下标0）。
- `Node<E> node = new Node<>(element);` —— 创建新节点，装着要插入的数据。
- `node.next = prev.next;` —— **关键第一步**：先让新节点的 `next`，指向"原本在 `index` 位置上的那个节点"（也就是 `prev` 当前指向的下一个）。这一步必须**先做**，否则一旦下一步把 `prev.next` 改掉，原来那个节点的引用就永久丢失了，找不回来了。
- `prev.next = node;` —— **关键第二步**：再把 `prev` 的 `next`，改成指向新节点。这两步顺序**不能反**，这是链表插入操作的标准套路。
- `size++;` —— 元素个数加一。

**图示一下这两步（假设在下标1插入新节点 D，原链表是 `head → A → B → C → null`）：**

```
插入前：  head → A → B → C → null
                    ↑
                  prev（假设index=1，prev停在A上）

第一步 node.next = prev.next：
          node(D).next 指向 B
          head → A → B → C → null
                    ↑    ↑
                  prev  node(D)

第二步 prev.next = node：
          A 的 next 改成指向 D
          head → A → D → B → C → null
```

## 3. `toString()`——用来打印整条链表，方便调试验证

```java
@Override
public String toString() {
    StringBuilder builder = new StringBuilder();
    Node<E> node = head.next;   // 从第一个结点开始，一个一个遍历，遍历一个就拼接到字符串上去
    while (node != null) {
        builder.append(node.element).append(" ");
        node = node.next;
    }
    return builder.toString();
}
```

- `Node<E> node = head.next;` —— 注意是从 `head.next` 开始遍历，不是从 `head` 开始，因为 `head` 本身不存真实数据（哨兵），第一个真实数据在 `head.next`。
- `while (node != null) { ... }` —— 一直遍历到 `next` 为 `null`（也就是链表末尾）为止，这是链表遍历的标准写法，之前也反复出现过。
- `builder.append(node.element).append(" ");` —— 把当前节点的数据拼进结果字符串，用空格隔开。
- `node = node.next;` —— 移动到下一个节点。

## 4. 加上范围校验的完整插入方法

```java
public void add(E element, int index){
    if(index < 0 || index > size)
        throw new IndexOutOfBoundsException("插入位置非法，合法的插入位置为：0 ~ "+size);
    Node<E> prev = head;
    for (int i = 0; i < index; i++)
        prev = prev.next;
    Node<E> node = new Node<>(element);
    node.next = prev.next;
    prev.next = node;
    size++;
}
```

这里多了一行校验：`index < 0 || index > size` 会抛异常。**注意这里的合法范围是 `[0, size]`**（能等于 `size`，表示"插入到末尾"），跟之前顺序表 `ArrayList` 的插入校验规则是一模一样的道理。

## 5. 删除操作

```java
public E remove(int index){
    if(index < 0 || index > size - 1)   // 同样的，先判断位置是否合法
        throw new IndexOutOfBoundsException("删除位置非法，合法的删除位置为：0 ~ "+(size - 1));
    Node<E> prev = head;
    for (int i = 0; i < index; i++)   // 同样需要先找到前驱结点
        prev = prev.next;
    E e = prev.next.element;   // 先把待删除结点存放的元素取出来
    prev.next = prev.next.next;  // 可以删了
    size--;   // 记得size--
    return e;
}
```

- 校验范围是 `[0, size-1]`（删除必须是已存在的位置，跟插入不一样，插入可以是"末尾+1"这个位置）。
- `Node<E> prev = head;` + 循环 —— 同样是先找到"待删除节点"的**前驱节点**（这是链表操作的通用套路，删除、插入都得先找前驱）。
- `E e = prev.next.element;` —— `prev.next` 就是真正要删除的那个节点，先把它的数据取出来保存，因为下一行操作完之后，这个节点的引用就没法再直接拿到了。
- `prev.next = prev.next.next;` —— **核心删除逻辑**：让 `prev` 直接"跳过"待删除节点，指向待删除节点的下一个。这一步执行完，待删除节点已经没有任何引用指向它了（原本指向它的只有 `prev.next`，现在这个引用已经被改掉），会被垃圾回收自动清理。
- `size--;` —— 元素个数减一。
- `return e;` —— 返回被删除的元素，这也是"删除方法通常要返回被删元素"的标准设计（呼应你之前问过的顺序表 `remove` 也是同样的返回设计）。

**图示（删除下标1的节点B，原链表 `head → A → B → C → null`）：**

```
删除前:  head → A → B → C → null
                  ↑    ↑
                prev  待删除节点(prev.next)

执行 prev.next = prev.next.next：
        A 的 next 直接指向 C，跳过了 B
删除后:  head → A → C → null
                          B 没有任何引用指向它了，等待被GC回收
```

## 6. 获取指定位置的元素

```java
public E get(int index){
    if(index < 0 || index > size - 1)
        throw new IndexOutOfBoundsException("非法的位置，合法的位置为：0 ~ "+(size - 1));
    Node<E> node = head;
    while (index-- >= 0)   // 这里直接让index减到-1为止
        node = node.next;
    return node.element;
}

public int size(){
    return size;
}
```

这里 `while (index-- >= 0)` 这行是最容易看不懂的地方，我拆开讲一下这个"先判断再自减"的技巧：

- `index--` 是**后缀自减**：**先使用 `index` 当前的值参与判断，判断完之后，`index` 才减1**。
- 假设 `index = 2`（要找下标2的元素）：

|循环轮次|判断时index的值|判断结果|判断后index变成|node移动|
|---|---|---|---|---|
|第1次|2|`2 >= 0` 为真，继续循环|1|node = node.next（第1步）|
|第2次|1|`1 >= 0` 为真，继续循环|0|node = node.next（第2步）|
|第3次|0|`0 >= 0` 为真，继续循环|-1|node = node.next（第3步）|
|第4次|-1|`-1 >= 0` 为假，退出循环|-2（但已经不重要了）|不再移动|

一共移动了 **3次**（`index + 1` 次），从 `head` 出发移动3步，正好停在"下标2"的真实节点上（`head` 走1步到下标0，走2步到下标1，走3步到下标2）。

这里其实和之前讲的 `for (int i = 0; i < index; i++) prev = prev.next;`（在 `add`/`remove` 里用的写法）本质效果不完全一样——**注意 `get` 这里 `node` 一开始是 `head`，需要走 `index+1` 步才能到目标节点**；而 `add`/`remove` 里 `prev` 只需要走 `index` 步，因为它要找的是"目标位置的前一个"，不是目标位置本身。这个细节上的差异，正好体现了"找某个位置本身"和"找某个位置的前驱"，需要移动的步数是不一样的，写代码时要留意这种"差一"的边界情况。

- `return node.element;` —— 循环结束后，`node` 停在目标节点上，返回它的数据。

---

## 📌 总结

|方法|核心逻辑|
|---|---|
|`add(element, index)`|先找到 `index` 位置的**前驱节点** `prev`，再"先接住原来的下一个，再改前驱的指向"（顺序不能反），最后 `size++`|
|`remove(index)`|同样先找前驱 `prev`，取出待删除节点的数据，让 `prev.next` 直接跳过待删除节点，最后 `size--`|
|`get(index)`|从 `head` 出发，走 `index+1` 步（注意比 `add`/`remove` 里的循环多走一步，因为要找的是节点本身而不是前驱）|
|`toString()`|从 `head.next`（第一个真实节点）开始遍历到 `null`，逐个拼接|

所有操作的共同点是：**链表没有下标可以直接"跳"过去，必须靠 `next` 一步步走**；**要操作（插入/删除）某个位置的节点，必须先找到它的前驱节点**，这是链式结构和数组结构最根本的操作差异。

## 🔍 拓展一下

- **插入操作里"先接住下一个，再改前驱指向"这个顺序，是整段代码里最容易出错也最重要的细节**：如果写反了（先 `prev.next = node`，再 `node.next = prev.next`），第二行的 `prev.next` 这时候已经变成了新节点自己，会导致 `node.next` 指向自己，整条链表从这里开始就"断裂"或者"死循环"了。这跟之前你实现 `MyLinkedList` 时反转链表那道题里"要先用变量记下原来的 `next`，再修改"是同一个原则——**凡是要修改一个引用的指向，如果这个引用原来的值后面还要用，必须先把它存到一个临时变量（或者利用好赋值的先后顺序）里，避免"改了之后找不到原来的东西"**。
    
- **原文里提到"什么情况下用顺序表，什么情况下用链表"这个对比，值得牢牢记住**：顺序表（数组）读取快（下标直接定位，`O(1)`），但插入删除慢（要挪动元素，`O(n)`）；链表插入删除快（改指针就行，`O(1)`，前提是已经找到位置），但读取慢（必须从头一步步走，`O(n)`）。这也是为什么标准库里 `ArrayList` 和 `LinkedList` 会同时存在，实际开发中要根据"是读多还是改多"来选择用哪一种。
    
- **栈和队列，其实就是"限制了操作方式的链表"**：原文接下来讲的 `LinkedStack`（栈，只能在头部进出，先进后出）和 `LinkedQueue`（队列，头部出、尾部进，先进先出），底层用的 `Node` 定义和这里的链表几乎一模一样，只是**限制了只能在特定的位置进行插入删除操作**（栈只操作头部，队列头部出尾部进），这也说明了数据结构之间是有传承关系的——理解透了链表的插入删除原理，栈和队列基本上就是把这套逻辑简化、限定使用场景之后的产物，理解起来会容易很多。如果你想深入这部分，我也可以专门详细讲一下栈和队列的实现细节。



### 线性表：栈

栈是在链表基础上"加限制"实现的一种数据结构——你会发现这段代码用到的知识点，跟你上一轮学的链表几乎完全一样（`Node`、`head`、改指针），只是操作被限定在了链表的**头部**。我逐行讲清楚，并且重点对比一下这跟普通链表的 `add()`/`remove()` 有什么区别。

## 1. 先理解"先进后出"这个核心特性

栈的关键规则是：**只能在同一端（栈顶）进出**。想象往一个只有一个开口的箱子里叠书——最后放进去的书，永远是最先能拿出来的那本，因为你没法绕过它去拿下面的书。这就是"先进后出"（FILO，First In, Last Out）。

对应到代码里的验证：

```java
stack.push("AAA");   // AAA 第一个进
stack.push("BBB");   // BBB 第二个进
stack.push("CCC");   // CCC 第三个进（最后进）

stack.pop();   // 输出 CCC —— 最后进的，最先出
stack.pop();   // 输出 BBB
stack.pop();   // 输出 AAA —— 第一个进的，最后出
```

## 2. 类的基本结构

```java
public class LinkedStack<E> {

    private final Node<E> head = new Node<>(null);   // 大体内容跟链表类似

    private static class Node<E> {
        E element;
        Node<E> next;

        public Node(E element) {
            this.element = element;
        }
    }
}
```

这部分跟你上一轮学的 `LinkedList` 一模一样——同样是一个不存数据的哨兵头节点 `head`，同样的 `Node<E>` 内部类结构。**唯一的区别在于接下来的操作方法**：`LinkedList` 支持在**任意位置**插入删除（`add(element, index)`），而 `LinkedStack` 只允许在**头部**（紧跟着 `head` 的那个位置）进出，这也是"栈"这种数据结构相比普通链表最本质的差别——**不是数据结构变了，而是允许的操作变少了**。

## 3. push() 入栈操作——逐行拆解

```java
public void push(E element){
    Node<E> node = new Node<>(element);   // 直接创建新结点
    node.next = head.next;    // 新结点的下一个变成原本的栈顶结点
    head.next = node;     // 头结点的下一个改成新的结点
}
```

- `Node<E> node = new Node<>(element);`：创建一个新节点，包装要入栈的数据。
- `node.next = head.next;`：**关键第一步**——让新节点的 `next`，先指向"目前 `head.next` 指向的节点"，也就是**当前的栈顶节点**（如果栈是空的，`head.next` 是 `null`，这一步就是让新节点的 `next` 变成 `null`，也完全没问题）。
- `head.next = node;`：**第二步**——把 `head.next` 改成指向新节点，新节点正式成为新的栈顶。

如果你回顾一下上一轮讲的链表 `add(element, 0)`（在**下标0的位置**插入），会发现代码逻辑几乎一模一样：

```java
// 链表 add(element, 0) 的逻辑（prev 一步都不用走，直接就是 head）
Node<E> prev = head;
Node<E> node = new Node<>(element);
node.next = prev.next;   // 等价于 node.next = head.next
prev.next = node;         // 等价于 head.next = node
```

**`push()` 本质上就是"永远在链表最前面插入一个新节点"**——因为不需要考虑插入到中间位置，所以连"先找前驱节点"那个 `for` 循环都省了，直接用 `head` 当前驱节点，这也是为什么笔记里说"使用链表实现栈会更方便"：栈天然只在一端操作，正好避开了链表操作里最麻烦的"要遍历找位置"这一步。

## 4. pop() 出栈操作——逐行拆解

```java
public E pop(){
    if(head.next == null)   // 如果栈已经没有元素了，那么肯定是没办法取的
        throw new NoSuchElementException("栈为空");
    E e = head.next.element;   // 先把待出栈元素取出来
    head.next = head.next.next;   // 直接让头结点的下一个指向下一个的下一个
    return e;
}
```

- `if(head.next == null) throw new NoSuchElementException("栈为空");`：**空栈校验**——`head.next == null` 说明头节点后面什么都没有，栈是空的，这时候没有任何元素可以弹出，直接抛出异常拦截（这里用的是 `NoSuchElementException`，跟之前顺序表、链表用的 `IndexOutOfBoundsException` 不一样，因为这里的问题不是"下标越界"，而是"压根没有元素可取"，异常类型选得更贴切）。
- `E e = head.next.element;`：**先把栈顶元素的值取出来**，暂存到局部变量 `e`，因为紧接着这个节点就要被摘掉了，不提前存下来就再也拿不到了——这跟上一轮链表 `remove()` 方法"先取值再删除"的顺序是同一个道理。
- `head.next = head.next.next;`：**核心出栈操作**——让头节点直接跳过原来的栈顶节点，指向"栈顶的下一个节点"，原栈顶节点就变成了新的栈顶。这行代码也完全对应上一轮链表 `remove(0)`（删除下标0）的逻辑：

```java
// 链表 remove(0) 的逻辑（prev 直接就是 head，不用循环找）
Node<E> prev = head;
E e = prev.next.element;
prev.next = prev.next.next;   // 等价于 head.next = head.next.next
```

- `return e;`：把之前暂存的值返回给调用者。

结合测试代码，画一下内存里链表结构的变化过程：

```
初始状态：           head → null

push("AAA")：        head → [AAA] → null
push("BBB")：        head → [BBB] → [AAA] → null   （新节点总是插在最前面）
push("CCC")：        head → [CCC] → [BBB] → [AAA] → null

pop() 第一次：
  取值：e = head.next.element = "CCC"
  摘除：head.next = head.next.next，也就是 head → [BBB] → [AAA] → null
  返回："CCC"

pop() 第二次：
  取值：e = "BBB"
  摘除：head → [AAA] → null
  返回："BBB"

pop() 第三次：
  取值：e = "AAA"
  摘除：head → null
  返回："AAA"
```

可以清楚看到，"栈顶"这个概念，在链表实现里，永远对应的就是 `head.next` 指向的那个节点——**入栈永远往最前面插，出栈永远从最前面取**，这正是为什么用链表实现栈会特别自然、代码特别简洁的原因。

## 📌 总结

- **栈是一种"只能在一端（栈顶）进出"的特殊线性表**，规则是**先进后出（FILO）**——最后压入的元素，最先被弹出。
- 用链表实现栈，核心思路是：**把 `head.next` 指向的节点，当作"栈顶"**。
- `push()` 就是"永远在链表最前面插入新节点"：先让新节点接住原来的栈顶（`node.next = head.next`），再让 `head` 指向新节点（`head.next = node`）。
- `pop()` 就是"永远从链表最前面取出并删除节点"：先取值，再让 `head` 跳过原栈顶、直接指向下一个节点（`head.next = head.next.next`）。
- `push()`/`pop()` 本质上都是**上一轮链表 `add(element, 0)`/`remove(0)` 的简化版**——因为固定操作头部这一个位置，不需要再写"寻找前驱节点"的循环，代码比通用链表的插入删除更简单。

## 🔍 拓展一下

- **为什么不选"在链表尾部"进出，而是选"头部"？**——这是效率上的考量。如果栈选择在链表**尾部**操作，那么每次 `push`/`pop` 都得先遍历整条链表找到最后一个节点（就像笔记后面队列实现里的 `offer()` 方法那样，需要一个 `while` 循环走到底），时间复杂度是 O(n)；而选择在**头部**操作，因为 `head` 本身就是固定的、随时能拿到的引用，不需要任何遍历，`push`/`pop` 的时间复杂度都是 **O(1)**，效率上有本质区别。这也是为什么设计者特意选择"头部"作为栈顶。
    
- **栈在实际编程中无处不在，最直接的例子就是方法调用**：之前讲递归（比如反转链表的递归版本）时提到过"方法调用栈"，这正是"栈"这种数据结构最经典的应用——每次调用一个方法，就相当于"压入"一个新的栈帧；方法执行完返回，就相当于"弹出"这个栈帧。方法调用天然符合"后调用的方法，先执行完、先返回"这个规律，跟栈的先进后出完全吻合，这也是为什么递归调用太深会导致"栈溢出（StackOverflowError）"——本质上就是这个"栈"被压得太满，超出了容量限制。
    
- **顺序表实现栈会更简单，效率也不差，可以对比着写一遍加深理解**：如果用数组实现栈，`push` 就是往数组末尾追加一个元素（`array[size++] = element`），`pop` 就是取出数组末尾的元素再把 `size` 减一（`array[--size]`），都不需要挪动任何其他元素，同样是 O(1)，甚至比链表版本更省内存（不需要额外存 `next` 引用）。Java 标准库里的 `java.util.ArrayDeque`（作为栈使用时）用的正是数组实现，而不是链表，实际开发中反而更常见，感兴趣的话可以自己动手把这次的 `LinkedStack` 改写成顺序表版本练练手，会对"同一种逻辑抽象，可以用不同底层结构实现"这件事有更深的体会。



### 线性表：队列
队列跟你刚学的栈是"同宗兄弟"——底层结构一样（`Node` + `head`），区别只在于"进"和"出"分别发生在哪一端。栈是"一头进一头出（同一头）"，队列是"一头进一头出（不同头）"，这个区别决定了两者代码实现上的关键差异。我逐行讲清楚，并且重点分析一下这版代码里一个**性能上的隐藏问题**，笔记原文其实提示了但代码没完全体现出来。

## 1. 先理解"先进先出"和队列的两个端点

队列的规则是：**只能从一端（队尾）进入，从另一端（队首）离开**。就像排队买饭——先来的人先打到饭，新来的人只能排在队伍最后面。

```java
queue.offer("AAA");   // AAA 第一个进（排在最前）
queue.offer("BBB");   // BBB 第二个进（排在AAA后面）
queue.offer("CCC");   // CCC 第三个进（排在最后面）

queue.poll();   // 输出 AAA —— 最先进的，最先出
queue.poll();   // 输出 BBB
queue.poll();   // 输出 CCC —— 最后进的，最后出
```

这跟上一轮的栈（后进先出）正好相反——**队列的"入队顺序"和"出队顺序"完全一致**。

## 2. 类的基本结构

```java
public class LinkedQueue<E> {

    private final Node<E> head = new Node<>(null);

    private static class Node<E> {
        E element;
        Node<E> next;

        public Node(E element) {
            this.element = element;
        }
    }
}
```

跟栈完全一样的哨兵头节点 `head` 和 `Node<E>` 内部类，不再重复讲。

## 3. offer() 入队操作——逐行拆解

```java
public void offer(E element){  // 入队操作
    Node<E> last = head;
    while (last.next != null)   // 入队直接丢到最后一个结点的屁股后面就行了
        last = last.next;
    last.next = new Node<>(element);
}
```

- `Node<E> last = head;`：从头节点出发，准备找到链表**当前的最后一个节点**。
- `while (last.next != null) last = last.next;`：这是**遍历找到链表末尾**的标准写法——只要当前节点还有"下一个"，就继续往后走；循环停下来的时候，`last` 正好停在"最后一个节点"上（它的 `next` 是 `null`）。这跟你之前实现链表 `add()` 的思路完全一致（上一轮讲过的"链表基础"里的 `toString()` 遍历用的也是同一种判断方式）。
- `last.next = new Node<>(element);`：把新节点直接接在这个"最后一个节点"的后面，完成入队。

## 4. poll() 出队操作——逐行拆解

```java
public E poll(){   // 出队操作
    if(head.next == null)   // 如果队列已经没有元素了，那么肯定是没办法取的
        throw new NoSuchElementException("队列为空");
    E e = head.next.element;
    head.next = head.next.next;   // 直接从队首取出
    return e;
}
```

这段代码你应该很眼熟——**它跟上一轮栈的 `pop()` 方法一模一样**！

```java
// 对比：栈的 pop()
public E pop(){
    if(head.next == null)
        throw new NoSuchElementException("栈为空");
    E e = head.next.element;
    head.next = head.next.next;
    return e;
}
```

这不是巧合——**队列的"取出端"（队首）和栈的"取出端"（栈顶）刚好都在链表的最前面（`head.next`）**，所以"取出"这个动作的代码写法完全一致：判空、取值、让 `head.next` 跳过被取出的节点。

**真正的区别只在"放入端"**：

- 栈的 `push()` 是往**最前面**插（跟"取出端"是同一头，所以叫"先进后出"）。
- 队列的 `offer()` 是往**最后面**插（跟"取出端"是不同的两头，所以叫"先进先出"）。

这正是队列和栈最本质的区别——**一个"进"和"出"在同一端，一个不在同一端**，其他部分的实现思路是完全相通的。

## 5. 用图示走一遍完整流程

```
初始状态：            head → null

offer("AAA")：
  last 从 head 出发，head.next 是 null，循环不执行，last 就是 head
  head.next = new Node("AAA")
  结果：head → [AAA] → null

offer("BBB")：
  last 从 head 出发，head.next 不是 null（指向AAA），last 走到 [AAA]
  [AAA].next 是 null，循环停止，last 停在 [AAA]
  [AAA].next = new Node("BBB")
  结果：head → [AAA] → [BBB] → null

offer("CCC")：
  last 从 head 走到 [AAA]，再走到 [BBB]（因为要一直走到最后一个）
  [BBB].next = new Node("CCC")
  结果：head → [AAA] → [BBB] → [CCC] → null

poll() 第一次：
  e = head.next.element = "AAA"
  head.next = head.next.next，结果：head → [BBB] → [CCC] → null
  返回："AAA"

poll() 第二次：
  e = "BBB"
  结果：head → [CCC] → null
  返回："BBB"

poll() 第三次：
  e = "CCC"
  结果：head → null
  返回："CCC"
```

可以看到，出队顺序 `AAA → BBB → CCC`，跟入队顺序完全一致，这就是"先进先出"。

## 6. 这版代码有一个值得注意的性能问题

笔记原文其实已经提示了这一点："**注意我们需要同时保存队首和队尾两个指针**……队尾则直接是指向尾结点的指针即可，后面只需要直接在后面拼接就行"，但截图里实际给出的代码，**并没有真正维护"队尾指针"这个字段**，`offer()` 方法每次都要用 `while` 循环从头遍历到尾：

```java
public void offer(E element){
    Node<E> last = head;
    while (last.next != null)   // 每次入队，都要从头走到尾，效率是 O(n)
        last = last.next;
    last.next = new Node<>(element);
}
```

如果队列里已经有1000个元素，第1001次 `offer()` 就得往后走1000步才能找到末尾——**这跟笔记文字描述的"设计思路"其实是不一致的，属于示例代码里一个可以优化的地方**。真正理想的实现，应该**额外维护一个 `tail` 字段，始终指向当前的最后一个节点**：

```java
public class LinkedQueue<E> {
    private final Node<E> head = new Node<>(null);
    private Node<E> tail = head;   // 队尾指针，初始时队列为空，tail 和 head 指向同一个位置

    public void offer(E element){
        Node<E> newNode = new Node<>(element);
        tail.next = newNode;   // 直接接在 tail 后面，不需要遍历
        tail = newNode;         // tail 更新为新节点，随时保持"指向最后一个"
    }

    public E poll(){
        if(head.next == null)
            throw new NoSuchElementException("队列为空");
        E e = head.next.element;
        head.next = head.next.next;
        if (head.next == null) {   // 如果删完之后队列空了，tail 需要重新指回 head，防止 tail 变成野指针
            tail = head;
        }
        return e;
    }

    private static class Node<E> {
        E element;
        Node<E> next;
        public Node(E element) {
            this.element = element;
        }
    }
}
```

加上 `tail` 之后，`offer()` 直接用 `tail.next = newNode` 一步到位，时间复杂度从 O(n) 降到了 **O(1)**，跟 `poll()` 的效率保持一致。

## 📌 总结

- **队列是"一端进（队尾），另一端出（队首）"的线性表**，规则是**先进先出（FIFO）**——先进队的元素，先出队。
- `poll()` 出队的代码跟栈的 `pop()` 完全一样，因为两者的"取出端"都是链表最前面（`head.next`）。
- `offer()` 入队的实现方式，是队列和栈的核心区别——队列往链表**末尾**插，栈往链表**最前面**插。
- 截图给出的 `offer()` 实现，每次都要遍历到链表末尾（O(n)），跟笔记文字里提到的"应该维护队尾指针"这个设计思路不完全一致；真正高效的实现应该额外维护一个 `tail` 字段，让入队操作也能做到 O(1)。

## 🔍 拓展一下

- **把这次的栈和队列放一起对比记忆，会发现它们其实是"同一套链表骨架，插入位置不同"的两个变体**：
    
    ||入口操作|出口操作|特点|
    |---|---|---|---|
    |栈|`push`：插在链表头部|`pop`：从链表头部取出|进出同一端，O(1)|
    |队列（有 `tail`）|`offer`：插在链表尾部|`poll`：从链表头部取出|进出不同端，都是 O(1)|
    |队列（无 `tail`，本节示例代码）|`offer`：需要遍历到尾部才能插|`poll`：从链表头部取出|入队 O(n)，效率不理想|
    
    这也说明了一件事：**同一种"抽象概念"（先进先出/先进后出），底层用什么数据结构实现、怎么维护指针，会直接决定性能的好坏**，这也是数据结构这门课要重点关注的地方——不仅要写出"能跑"的代码，还要考虑"跑得快不快"。
    
- **双端队列（Deque，Double-Ended Queue）是队列的进阶版本**：既支持在队首进出，也支持在队尾进出（相当于同时具备栈和队列的能力），Java 标准库里的 `java.util.ArrayDeque`、`java.util.LinkedList`（它本身也实现了 `Deque` 接口）都是这种结构。如果链表本身是**双向链表**（之前提到过，节点同时存 `prev` 和 `next`），实现双端队列的删除队尾元素这种操作会容易很多，因为不需要遍历就能直接拿到"倒数第二个节点"。
    
- **Java 标准库里真正的 `Queue` 接口设计，可以拿来对照学习**：`java.util.Queue` 接口定义了 `offer()`（入队）、`poll()`（出队）、`peek()`（查看队首但不取出）等标准方法名，跟这次自己实现的方法名完全对应——说明这份笔记的代码设计，其实是在模仿标准库的接口规范，等你后面学到 Java 集合框架（`Collection`、`Queue`、`Deque` 这些接口的继承关系）时，会发现今天亲手实现的这些"玩具版"数据结构，跟标准库的设计思路是高度一致的，这也是为什么老师会先带你从零手写一遍，再去学官方集合类——理解了底层原理，用起来会更得心应手，也更容易看懂源码。

### 哈希表
## 1. 先理解哈希表要解决什么问题

之前你学过的几种查找方式，各有各的短板：

- **顺序查找**（一个一个比对）：数据量大了效率很低。
- **二分查找**：效率高，但要求数据**必须有序**，而且不能随便增删（增删之后顺序就乱了，得重新排序）。
- **二叉查找树**（上一节的内容）：效率不错，但如果插入的数据碰巧是递增或递减的，树会退化成链表，效率打回原形（除非用平衡二叉树/红黑树维护平衡，但实现复杂）。

**哈希表提供了一种更直接的思路：不用比较、不用查找，直接"算"出数据应该在哪个位置。**

## 2. 哈希函数——数据和位置之间的"计算公式"

```
散列（Hashing）通过散列函数（哈希函数）将要参与检索的数据与散列值（哈希值）关联起来
```

哈希函数的核心特性是：**同一个数据，无论算多少次，得到的哈希值永远一样；不同的数据，算出来的哈希值大概率不一样**。这跟你之前学过的 `hashCode()` 方法是同一个概念——之前讲 `Object` 类的时候提过，每个对象都有一个 `hashCode()` 方法，能返回一个代表这个对象的整数。

## 3. 哈希表最简单的实现——直接用取模定位

```java
public class HashTable<E> {
    private final int TABLE_SIZE = 10;              // 表的固定大小，10个位置
    private final Object[] TABLE = new Object[TABLE_SIZE];   // 底层就是一个普通数组

    public void insert(E element){
        int index = hash(element);   // 先算出这个元素该放在哪个下标
        TABLE[index] = element;       // 直接存进去
    }

    public boolean contains(E element){
        int index = hash(element);      // 查找时，同样先算出应该在哪个位置
        return TABLE[index] == element; // 直接去这个位置看看是不是这个元素
    }

    private int hash(Object object){   // 哈希函数，计算出存放的位置
        int hashCode = object.hashCode();
        // 每一个对象都有一个独一无二的哈希值，可以通过hashCode方法得到（只有极小的概率会出现相同的情况）
        return hashCode % TABLE_SIZE;   // 用取模，把任意大的hashCode，压缩到 0~9 这个范围内
    }
}
```

逐行看：

- `TABLE_SIZE = 10`、`Object[] TABLE`：底层其实就是一个**普通数组**（跟你之前实现的顺序表用的是同一种存储方式），只是接下来"往哪个下标存"这件事，不再是你手动指定，而是靠哈希函数**自动算出来**。
- `hash(object)` 方法：先拿到这个对象的 `hashCode()`（一个可能很大、很分散的整数），再用 `% TABLE_SIZE` **取模**，把它压缩到 `0 ~ TABLE_SIZE-1` 这个范围内——这正是你上一轮问的 `hash(27) = 27 % 9 = 0` 那个计算的原理，只是这里换成了 `% 10`。
- `insert()`：算出下标，直接把元素存进数组对应位置，**不需要遍历、不需要比较**。
- `contains()`：同样先算出下标，直接去这一个位置看有没有这个元素——**不管数据总量有多大，查找永远只需要"算一次哈希值 + 访问一次数组"，时间复杂度是 O(1)**，这正是哈希表最大的优势，比之前任何一种查找方式都快。

## 4. 但这个简单版本有一个大问题——哈希碰撞

```
比如现在同时插入14和23这两个元素，他们两个计算出来的哈希值是一样的，都需要在5号下标位置插入
```

因为哈希函数是"压缩"数据（把无限多种可能的数据，压缩进只有 `TABLE_SIZE` 个格子里），**不同的数据算出相同哈希值，是数学上必然会发生的事情**（格子数量有限，数据可能无限，鸽笼原理）。这种情况叫**哈希碰撞（哈希冲突）**。

上面那个简单版本的代码完全没处理这个问题——如果14和23都要存到下标5，后插入的会**直接覆盖**先插入的，数据就丢了，这是不能接受的。

## 5. 解决哈希碰撞——链地址法（结合你已经学过的链表）

```
实际常见的哈希冲突解决方案是链地址法，当出现哈希冲突时，我们依然将其保存在对应的位置上，我们可以将其连接为一个链表的形式
```

思路是：**数组的每一个位置，不再直接存一个元素，而是存一条链表的入口**。如果多个元素的哈希值算出来相同，就都挂在同一个位置的链表上，一个接一个串起来，而不是互相覆盖。

这正是这一整章前面学的东西第一次"组合应用"——**哈希表的每个格子，其实就是你上一节实现的那种带哨兵头节点的链表**。

```java
public class HashTable<E> {
    private final int TABLE_SIZE = 10;
    private final Node<E>[] TABLE = new Node[TABLE_SIZE];   // 数组里存的不再是元素本身，而是每个位置对应链表的"头节点"

    public HashTable(){
        for (int i = 0; i < TABLE_SIZE; i++)
            TABLE[i] = new Node<>(null);   // 初始化时，给每个位置都预先创建一个哨兵头节点（跟你之前学的head思路一样）
    }

    public void insert(E element){
        int index = hash(element);        // 先算出该往哪条链表插
        Node<E> prev = TABLE[index];      // 从这条链表的头节点出发
        while (prev.next != null)          // 一路走到链表末尾（跟上一轮队列 offer() 的写法一模一样）
            prev = prev.next;
        prev.next = new Node<>(element);   // 把新元素接到这条链表的末尾
    }

    public boolean contains(E element){
        int index = hash(element);              // 先定位到应该在哪条链表
        Node<E> node = TABLE[index].next;       // 从这条链表的第一个真实数据节点开始
        while (node != null) {                    // 挨个遍历这条链表（因为哈希碰撞，可能不止一个元素）
            if(node.element == element)
                return true;
            node = node.next;
        }
        return false;   // 走到链表末尾都没找到，说明确实没有这个元素
    }

    private int hash(Object object){
        int hashCode = object.hashCode();
        return hashCode % TABLE_SIZE;
    }

    private static class Node<E> {
        private final E element;
        private Node<E> next;
        private Node(E element){
            this.element = element;
        }
    }
}
```

- `Node<E>[] TABLE`：数组的每一个格子，不再是"一个元素"，而是"一条链表的头"——**数组解决"快速定位大致区域"，链表解决"同一区域里有多个数据怎么共存"**，两种数据结构强强联合。
- 构造方法里的循环 `for (int i = 0; i < TABLE_SIZE; i++) TABLE[i] = new Node<>(null);`：给数组的每一个位置，都预先放一个哨兵头节点，跟你上一轮学的链表、队列的 `head` 是同一个设计思路——**保证每个位置从一开始就是一条"合法但为空"的链表，不用再单独判断"这个位置是不是 null"**。
- `insert()` 里 `while (prev.next != null) prev = prev.next;`：这一段代码，跟你上一节 `LinkedQueue.offer()` 的写法**完全一样**——都是"走到链表末尾，把新节点接上去"。
- `contains()` 里的遍历查找：如果两个元素哈希值一样（都在同一个位置），就得在这条短链表里**挨个比较**才能确认到底有没有——这也是为什么哈希碰撞会拖慢效率，极端情况下（所有数据都碰撞到同一个位置），哈希表会退化成一条长链表，查找效率变成 O(n)，跟"二叉查找树插入递减数据会退化成链表"是同一类问题。

## 6. 哈希碰撞多了怎么办——转成树，进一步优化

```
比如当链表长度达到8时，自动转换为一棵平衡二叉树或是红黑树，这样就可以在一定程度上缓解查找的压力了
```

这句话正好把你前面刚学的**平衡二叉树、红黑树**和这里的哈希表连起来了——如果某个位置的链表变得很长（说明这个位置碰撞太严重），可以把这条链表**转换成一棵红黑树**，因为树的查找效率（O(log n)）比链表遍历（O(n)）要快得多。**这正是 Java 官方 `HashMap` 的真实实现方式**，笔记这里已经在为你后面学 `HashMap` 源码做铺垫了。

## 7. 用一张图总结哈希表的完整结构

```
数组（TABLE）：
下标0: head → null
下标1: head → null
下标2: head → null
...
下标5: head → [14] → [23] → null   （14和23哈希碰撞，串成了一条链表）
...
下标8: head → [17] → null
下标9: head → null
```

查找一个元素的完整流程：**先用哈希函数算出应该去哪个下标（一步到位，O(1)），再在这个位置对应的链表里挨个比对（如果没碰撞，链表只有一个元素，等于也是O(1)；如果碰撞多，链表变长，退化成O(n)）**。

## 📌 总结

- **哈希表的核心思路**：用哈希函数把数据的关键字（比如 `hashCode()`）压缩映射成一个数组下标，插入和查找都直接靠"算下标"完成，不需要遍历比较，理想情况下时间复杂度是 **O(1)**，比顺序查找、二分查找、树查找都更快。
- **最简单的实现**（`Object[] TABLE`）有个致命缺陷：不同数据可能算出相同下标（**哈希碰撞**），会导致数据互相覆盖丢失。
- **链地址法**是解决哈希碰撞的标准方案：数组的每个位置不直接存元素，而是存一条链表的头节点，碰撞的元素都挂在同一条链表上，一个接一个串起来——**这正是数组 + 链表这两种基础数据结构的组合应用**。
- 如果某个位置的链表因为碰撞太多变得很长，可以进一步优化成红黑树，兼顾内存效率和查找效率——这是真实 `HashMap` 源码用的策略。

## 🔍 拓展一下

- **这一整节内容，其实是在为你之后学 Java 集合框架里的 `HashMap`、`HashSet` 打基础**：真实的 `HashMap` 底层实现，跟这里手写的 `HashTable` 思路几乎完全一致——`Object[] TABLE` 对应 `HashMap` 里的 `Node[] table` 数组，链地址法对应 `HashMap` 处理哈希冲突的方式，"链表长度达到8转红黑树"这句话甚至是 `HashMap` 源码里真实存在的一个具体阈值（`TREEIFY_THRESHOLD = 8`）。理解了这一节，等你后面正式学 `HashMap` 的时候，会发现很多"为什么要这样设计"的问题，其实这里已经埋好了答案。
    
- **为什么表长度最好选素数（质数）**：笔记里提到"哈希表长度最好是一个素数"，这是因为如果表长度和数据本身的分布规律有某种公约数关系（比如表长是偶数，而插入的数据大多也是偶数），取模之后会导致哈希值**过度集中**在少数几个位置，碰撞会特别严重；选素数作为表长，能让取模的结果分布得更均匀，这也是为什么你会看到很多哈希表实现默认容量喜欢选类似16这种2的幂（Java的`HashMap`其实用的是2的幂而不是素数，但通过更复杂的扰动函数来达到类似的均匀分布效果，这是一个更进阶的优化细节，等学到`HashMap`源码时可以专门展开）。
    
- **哈希函数不只是用来做哈希表，你之前提到的下载文件校验也是同一个原理**：笔记里提到的 SHA-256、MD5，本质上跟这里 `hashCode() % TABLE_SIZE` 是同一类工具（哈希函数），只是**目的不同**——哈希表用哈希函数是为了"快速定位存储位置"，文件校验用哈希函数是为了"验证内容有没有被篡改/损坏"（利用了"同一个内容永远算出同一个哈希值"这个特性）。这也说明"哈希"这个概念在计算机科学里应用极其广泛，不仅仅局限于数据结构这一个领域，后面你如果学到密码学、区块链相关的内容，也会反复遇到这个思想的各种变体应用。



### 反转链表

本题来自LeetCode：[206. 反转链表](https://leetcode.cn/problems/reverse-linked-list/)

给你单链表的头节点 head ，请你反转链表，并返回反转后的链表。

示例 1：

![img](https://assets.leetcode.com/uploads/2021/02/19/rev1ex1.jpg)

> 输入：head = [1,2,3,4,5]  
> 输出：[5,4,3,2,1]




```java
static LinkedList reverseList(LinkedList head) {   // 建议直接返回新头节点，而不是 void
    LinkedList prev = null;
    LinkedList curr = head;

    while (curr != null) {
        LinkedList next = curr.next;   // 提前保存"原本的下一个"（这里才是真正有必要的一步，因为马上要改curr.next了）
        curr.next = prev;               // 关键：修改的是"节点的字段" curr.next，不是局部变量
        prev = curr;
        curr = next;
    }

    return prev;   // 返回反转后的新头节点
}
```

```java
public static void main(String[] args) {
    LinkedList l5 = new LinkedList(5, null);
    LinkedList l4 = new LinkedList(4, l5);
    LinkedList l3 = new LinkedList(3, l4);
    LinkedList l2 = new LinkedList(2, l3);
    LinkedList l1 = new LinkedList(1, l2);

    LinkedList newHead = reverseList(l1);   // 从真正的头节点 l1 开始传

    // 验证结果
    LinkedList current = newHead;
    while (current != null) {
        System.out.print(current.val + " -> ");
        current = current.next;
    }
    System.out.println("null");
}
```

输出：`5 -> 4 -> 3 -> 2 -> 1 -> null`

### 括号匹配问题

本题来自LeetCode：[20. 有效的括号](https://leetcode.cn/problems/valid-parentheses/)

给定一个只包括 '('，')'，'{'，'}'，'['，']' 的字符串 s ，判断字符串是否有效。

有效字符串需满足：

1. 左括号必须用相同类型的右括号闭合。
2. 左括号必须以正确的顺序闭合。

示例 1：

> 输入：s = "( )"  
> 输出：true

示例 2：

> 输入：s = "( )[ ]{ }"  
> 输出：true

示例 3：

> 输入：s = "( ]"  
> 输出：false

**示例 4：**

> 输入：s = "( [ ) ]"  
> 输出：false

**示例 5：**

> 输入：s = "{ [ ] }"  
> 输出：true

题干很明确，就是需要我们去对这些括号完成匹配，如果给定字符串中的括号无法完成一一匹配的话，那么就表示匹配失败。实际上这种问题我们就可以利用前面学习的栈这种数据结构来解决，我们可以将所有括号的左半部分放入栈中，当遇到右半部分时，进行匹配，如果匹配失败，那么就失败，如果匹配成功，那么就消耗一个左半部分，直到括号消耗完毕。



```java
import java.util.Stack;

class Solution {
    public boolean isValid(String s) {
        Stack<Character> stack = new Stack<>();   // 用来存放"等待被匹配"的左括号

        for (char c : s.toCharArray()) {   // 遍历字符串的每一个字符
            if (c == '(' || c == '[' || c == '{') {
                stack.push(c);   // 遇到左括号，直接压栈
            } else {
                // 走到这里，说明c一定是右括号（')' 或 ']' 或 '}'）
                if (stack.isEmpty()) {
                    return false;   // 栈是空的，说明没有左括号能跟这个右括号匹配，直接无效
                }
                char top = stack.pop();   // 弹出栈顶的左括号，看看类型对不对
                if ((c == ')' && top != '(') ||
                    (c == ']' && top != '[') ||
                    (c == '}' && top != '{')) {
                    return false;   // 类型不匹配，比如弹出的是 ( 但当前是 ]，直接无效
                }
            }
        }

        return stack.isEmpty();   // 遍历完了，如果栈还有剩，说明有左括号没被匹配上，无效
    }
}
```
